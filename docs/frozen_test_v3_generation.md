# Frozen Test v3 generation design

Decisions (2026-09-11): contract `frozen-test-v3` (interference range equals
communication range), stratification by the protocol table of
`docs/frozen_test_v2_protocol.md`, and a multi-size topology catalogue
generated by the legacy generator (`docs/topology_catalogue.md`).

## Authoring lock

`benchmarks/frozen_test_v3_authoring_lock.json` freezes everything the v3
authoring round depends on, before any v3 request exists: the pipeline
sources and their tests, the scripts, the two prompt templates, the topology
catalogue and every topology file it names, the scheduling scalability
results, the policy code that must stay untouched, the whole Frozen Test v2
provenance chain, the campaign results, the documentation, and the build
files. Check it at any point with:

```bash
uv run python scripts/verify_evaluation_lock.py --lock benchmarks/frozen_test_v3_authoring_lock.json
```

It is deliberately not an evaluation lock: no v3 benchmark is sealed yet.
`benchmarks/evaluation_lock_v3.json` is written after sealing and records the
sealed request, gold, and manifest hashes together with the runtime settings
and the generator and adjudicator models, the way
`benchmarks/evaluation_lock_v2.json` does for v2.

If a locked file has to change during authoring, record why and re-issue the
lock rather than editing it in place.

## Topology catalogue exposed to the generators

`benchmarks/topologies/frozen_test_v3_llm_catalogue.json` maps seven
topology ids to their public properties and file hashes: `legacy30_seed7`
(30 nodes, communication range 18.0, the Frozen Test v2 topology) and
`topo50_seed0` through `topo300_seed0` (range 20.0, one per size from
`benchmarks/topologies/fixed_area100_r20`). Keeping `legacy30_seed7` gives
the catalogue two different communication ranges, so range-consistency
cases have more than one correct answer. The file has the shape accepted by
`--topology-catalogue`; the generator prompt reproduces its properties as a
table.

Selection rule, stated in the prompt and mirrored by the harness binding
rule: a topology is selected only by its exact id. A description without the
id is CLARIFY, an unlisted id is REJECT, and a topology id's generation seed
never becomes the scheduling seed.

## Stratification

Each generator produces 36 groups with a closed `protocol_category`:

| protocol_category | per generator | total | gold action |
|---|---:|---:|---|
| supported_default | 4 | 8 | EXECUTE |
| supported_configured | 4 | 8 | EXECUTE |
| supported_latency_target | 3 | 6 | EXECUTE |
| missing_information | 3 | 6 | CLARIFY |
| invalid_parameter | 4 | 8 | REJECT |
| unsupported_energy | 4 | 8 | UNSUPPORTED |
| unsupported_digital_twin_or_sync | 4 | 8 | UNSUPPORTED |
| unsupported_periodic | 3 | 6 | UNSUPPORTED |
| unsupported_topology_adaptation | 3 | 6 | UNSUPPORTED |
| unsupported_other_objective | 4 | 8 | UNSUPPORTED |

Per action: 22 EXECUTE, 6 CLARIFY, 8 REJECT, 36 UNSUPPORTED, matching the
protocol document. The pipeline validator treats a `protocol_category`
that disagrees with `proposed_gold_action` as a structural defect and
checks `self_check.protocol_category_counts`; the per-action quotas used at
seal time come from `self_check` as before (11 / 3 / 4 / 18 per batch).
The prompt also enforces the protocol's compositional-phrasing rule (at
least one third of unsupported groups without canonical names), mixed
requests, hard negatives, and the construction rules learned from the v2
adjudication.

## Prompts

Templates carry role placeholders:

- `docs/prompts/frozen_test_v3_generator_prompt.txt` (`{ROLE}` / `{ROLE_LOWER}`)
- `docs/prompts/frozen_test_v3_reviewer_prompt.txt` (`{BATCH}` / `{BATCH_LOWER}`)

Rendering is mechanical, so it is scripted rather than hand-edited:

```bash
uv run python scripts/render_frozen_test_v3_prompts.py --output-dir docs/prompts/delivered
```

The renderer substitutes the placeholders literally (JSON braces in the
output-schema section are untouched), refuses if any placeholder survives, is
write-once, and prints the SHA-256 of every file. It writes five files into
`docs/prompts/delivered/`:

| File | Delivered to |
|---|---|
| `frozen_test_v3_generator_A.txt` | generator A |
| `frozen_test_v3_generator_B.txt` | generator B |
| `frozen_test_v3_reviewer_batch_A.txt` | the model that did **not** generate Batch A |
| `frozen_test_v3_reviewer_batch_B.txt` | the model that did **not** generate Batch B |
| `frozen_test_v3_specification.txt` | reference copy; already embedded in both reviewer prompts |

Each reviewer file embeds sections 1 to 4 of the generation prompt, so an
adjudicator receives exactly one prompt file plus one blind batch. These
delivered files are what the seal step hashes.

## Independence of the generators and adjudicators

The prompt states that a generator has no access to previous benchmarks,
previous system failures, or previous model responses, and must not build
requests around an assumed implementation weakness. That rules out any
session that took part in building or analysing the system:

- the session that authored the v3 contract, prompts, catalogue, or pipeline
  cannot generate or adjudicate a v3 batch;
- the session that produced the Frozen Test v2 failure taxonomy cannot
  either, because it knows exactly which phrasings the system mishandles;
- each batch must be generated in a fresh context that receives only its
  rendered generator prompt;
- each blind batch must be adjudicated by the model that did not generate it,
  again in a fresh context receiving only the rendered reviewer prompt and the
  blind file.

Record for each of the four sessions which model, interface, and date was
used; that goes into the v3 model metadata file at seal time. Reusing the two
models of Frozen Test v2 is fine and keeps the comparison meaningful, as long
as the sessions are new and carry none of this project's context.

## Blinding

Frozen Test v2 used hand-made blind files that still carried `difficulty`,
`capability_category`, `ambiguity_risk` and, for REJECT groups,
`invalid_fields`; category names such as `negated_digital_twin` hint at the
gold action, so that review was not fully blind and the paper must say so.
For v3 the pipeline produces the blind copy:

```bash
uv run python -m frozen_test_v2 blind --benchmark benchmark_model_A_v3.json \
  --out benchmarks/frozen_test_v3/batch_a_blind.json
```

The copy contains only batch identity, group ids, and request texts.

## Workflow after both batches and both reviews exist

```bash
uv run python -m frozen_test_v2 reconcile \
  --batch-a benchmark_model_A_v3.json --review-of-a "Model-B blind review of Batch A v3.json" \
  --batch-b benchmark_model_B_v3.json --review-of-b "Model-A blind review of Batch B v3.json" \
  --contract frozen-test-v3 \
  --topology-catalogue benchmarks/topologies/frozen_test_v3_llm_catalogue.json \
  --out benchmarks/frozen_test_v3/reconciliation
```

Then `check-decisions` with the same `--contract` and `--topology-catalogue`
arguments, and finally `seal`:

```bash
uv run python -m frozen_test_v2 seal \
  --batch-a benchmark_model_A_v3.json --review-of-a "Model-B blind review of Batch A v3.json" \
  --batch-b benchmark_model_B_v3.json --review-of-b "Model-A blind review of Batch B v3.json" \
  --contract frozen-test-v3 \
  --topology-catalogue benchmarks/topologies/frozen_test_v3_llm_catalogue.json \
  --decisions benchmarks/frozen_test_v3/human_decisions.json \
  --model-metadata benchmarks/frozen_test_v3/model_metadata.json \
  --prompt generator_a=docs/prompts/delivered/frozen_test_v3_generator_A.txt \
  --prompt generator_b=docs/prompts/delivered/frozen_test_v3_generator_B.txt \
  --prompt reviewer_a=docs/prompts/delivered/frozen_test_v3_reviewer_A.txt \
  --prompt reviewer_b=docs/prompts/delivered/frozen_test_v3_reviewer_B.txt \
  --policy-version paper1-scope-policy.v2 \
  --source-commit <commit-or-archive-id> \
  --out benchmarks/frozen_test_v3/sealed
```

Every catalogue topology is hashed into the manifest; each entry of
`frozen_test_v3_llm_catalogue.json` carries a `path` relative to the project
root, so no `--topology-file` argument is needed when the command runs from
there.

## Running the sealed v3 benchmark

Export the evaluator-side harness as for v2
(`scripts/export_frozen_test_v2_harness.py`); it reads the catalogue from the
sealed manifest, so requests bind to whichever topology they name. A request
that names two catalogue topologies binds to none, which is the intended
reading of the ambiguous-selection CLARIFY cases.

The built-in runner resolves only the single legacy topology, so v3 uses a
catalogue-aware runner that leaves `experiments.py` untouched:

```bash
uv run python scripts/run_frozen_test_v3_experiments.py \
  --benchmark benchmarks/frozen_test_v3/harness/frozen_test_v3_harness.jsonl \
  --topology-catalogue benchmarks/topologies/frozen_test_v3_llm_catalogue.json \
  --raw-output results/frozen_test_v3/phi4_policy_v2.jsonl \
  --systems llm_agent --provider ollama --model phi4:14b \
  --temperature 0 --max-retries 2 --timeout-seconds 600 --seeds 0
```

It verifies every topology file against the catalogue hash, refuses before
writing anything if the benchmark names a topology the catalogue lacks, and
writes the same append-only, resumable ledger as the built-in runner, so
`summarize_experiments.py` and `compare_experiments.py` work unchanged.
