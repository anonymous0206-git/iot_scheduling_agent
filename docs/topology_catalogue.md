# Multi-size topology catalogue

Decision (2026-09-11): Frozen Test v3 and the scheduling scalability
experiment use topologies generated by the legacy generator in
`source/libs` (through `generate_network_instance`, which isolates the RNG
and enforces connectivity), with varying node counts, instead of an external
dataset. Every topology is stored as a JSON `NetworkInstance` together with
its baseline ANEX schedule so that both can be visualized.

## Generate

```bash
uv run python scripts/build_topology_catalogue.py \
  --output-dir benchmarks/topologies/fixed_area100_r20 \
  --sizes 50 100 150 200 250 300 --samples 30 \
  --area 100 --range 20 --working-period 10 --active-slots 2 \
  --baseline-channels 2 --prefix topo --llm-samples 0
```

Defaults reproduce the setting of the original ANEX experiments (square
coordinate domain 0..100, communication range 20, working period 10, two
active slots per node). The density therefore grows with the node count. A
fixed-density family can be produced by running the script again with a
different `--area` per size into another directory.

The script is write-once: it refuses to overwrite an existing catalogue or
topology file. Generation is deterministic; regenerating with the same
arguments yields byte-identical files.

## Outputs

| File | Content |
|---|---|
| `<prefix><N>_seed<S>.json` | `NetworkInstance` (nodes, coordinates, active slots, neighbor lists, statistics) |
| `<prefix><N>_seed<S>.baseline_schedule.json` | `SchedulingResult` of ANEX with the baseline channel count, alpha = 1, validated under `legacy_neighbor` |
| `catalogue.json` | generator settings, SHA-256 of every file, public properties (node count, edge count, degrees, BFS depth) and the baseline latency of every topology |
| `llm_catalogue.json` | the subset selected by `--llm-samples`, in the shape accepted by `python -m frozen_test_v2 ... --topology-catalogue` |

The topology id pattern is `<prefix><node_count>_seed<generation_seed>`; the
generation seed is part of the id and, as in Frozen Test v2, must never be
read as a scheduling seed. The legacy `legacy30_seed7` topology keeps its own
name and settings (domain 0..40, range 18).

## Visualize

```bash
uv run python -m agentic_anex.visualization animate \
  --network benchmarks/topologies/fixed_area100_r20/topo100_seed0.json \
  --schedule benchmarks/topologies/fixed_area100_r20/topo100_seed0.baseline_schedule.json \
  --slot-duration-ms 500 --output results/topologies/topo100_seed0_replay.html
```

`--schedule` accepts the saved `SchedulingResult` directly. The static
topology renderer (`python -m agentic_anex.visualization topology --network
...`) works on the same files.

## Scheduling scalability experiment

```bash
uv run python scripts/run_topology_scaling_experiment.py \
  --catalogue benchmarks/topologies/fixed_area100_r20/catalogue.json \
  --channels 1 2 3 4 5 6 7 --reference-channels 2 \
  --output-dir results/topology_scaling/fixed_area100_r20
```

For every catalogue topology and channel count the script runs ANEX through
the typed wrapper (alpha = 1), validates the schedule with the independent
validator under `legacy_neighbor`, and measures latency. It verifies each
topology file against the catalogue hash first, involves no language model,
and writes once: `runs.csv` (one row per topology and channel count),
`summary.csv` (mean, sd, 95% CI, min, max, validity, channels actually used
per node count and channel count), `paired_bootstrap.json` (latency
difference of each channel count against the reference count, paired by
topology, seeded bootstrap CI), and `manifest.json` (hashes and settings).
Seven is the largest useful channel count because the legacy channel
coloring allocates seven color buckets.

## How the catalogue feeds Frozen Test v3

- The generation prompt lists the public properties of every entry in
  `llm_catalogue.json` (one topology per size by default), so requests can
  name different topologies and the REJECT cases about working period and
  communication range have more than one correct answer.
- The pipeline commands take `--topology-catalogue
  benchmarks/topologies/fixed_area100_r20/llm_catalogue.json`.
- The experiment runner keeps `run_experiment_matrix` unchanged:
  `scripts/run_frozen_test_v3_experiments.py` supplies a catalogue-aware
  `topology_resolver` that loads each JSON file and checks it against the
  catalogue hash, so no locked file has to change.
- Sealing hashes every catalogue topology into the lock manifest. Entries
  that carry a `path` need no `--topology-file` argument; sealing is refused
  when a topology file is missing or has drifted from its catalogue hash.
